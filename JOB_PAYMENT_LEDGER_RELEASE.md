## Implemented

- A lost publication acknowledgement now recovers through verified invoice/order inspection when Square reports a collectible invoice and public URL. The local publication transaction records the URL/status and advances reconciliation generation; a fresh claim can attach the known replacement without republishing. Intercepted actual-SDK coverage verifies two GETs and no publication request. This does not solve an unknown order/invoice identity or establish a provider retry-retention duration. Square's [idempotency guide](https://developer.squareup.com/docs/build-basics/common-api-patterns/idempotency) explains duplicate-key behavior but the inspected page does not specify that duration; do not assume another provider's 24-hour rule applies.

- Replacement issuance is now connected to reconciliation behind `JOB_INVOICE_REPLACEMENT_ENABLED` plus the ledger, Square adapter and reconciliation flags. The service locks and rechecks the approved job/quote, saved request, current funding, old invoice set and any saved provider invoice before provider entry. It resumes a known published invoice directly at verified attachment; otherwise it calls the existing immutable-intent Square service with the saved request key, amount and due date. Square delivery is `none`; customer messages remain in the financial-notice outbox. Unattached replacement requests keep reconciliation retryable, including a saved draft. Actual-worker/disposable-SQL tests simulate an interrupted draft and published-but-unattached recovery, checking identical retry inputs, no repeat provider entry after publication, and one notice. The provider creation operation is stubbed in these tests. Full signed-provider acceptance, idempotency-retention expiry and operator resolution of changed or multiple requests remain open; all flags remain disabled in production. This supersedes the older implementation-open notes below, but not their live acceptance requirements.

- Canonical closeout approval survives invoice errors, including ambiguous provider responses. The token-authorized endpoint accepts a still-approved canonical request for recovery; the approval transaction resumes only with unchanged approved quote, total, current funding and recorded due date. It preserves the approval timestamp and invoice request identity without new writes. Disposable SQL tests cover replay and changed/missing evidence. Legacy mode retains its existing reset behavior. Full HTTP/provider failure acceptance and automatic replacement issuance remain open.

- Partial-funding recovery no longer completes reconciliation with a canceled invoice's stale balance/link. When all inspected final invoices are noncollectible and the completed job still has a valid customer-approved closeout, it commits the verified remainder to lead/closeout, clears the payment URL, retains the invoice binding for audit and leaves the queue retryable. Disposable worker coverage verifies rollback, no repeated cancellation, no premature customer notice and rejection of late attachment. Replacement invoice creation remains unfinished; this change does not create or send a replacement.

- Canonical final-invoice creation now commits immutable input in `square_invoice_intents` before entering the provider client. Stable request identity, quote/closeout, configured location, cents, due date, recipient, description and delivery mode are required and compared on retry. Storage failure or a lost commit response stops provider entry; replay preserves the original row. The service copies incoming objects and pins the recorded location for its order. Customer/order/invoice identities now persist in a separate phase table before constructing the next request. Saved phases skip provider lookups on retry; invoice version zero is retained and competing identities reject. Disposable checks cover missing intent, lost phase acknowledgements and identity conflicts. The actual service also replays an unacknowledged order with the same key/payload, retains the selected customer and skips saved phases after a later local persistence failure. Full signed-provider acceptance and recovery beyond provider idempotency retention remain open. Both additive intent tables are required before enabling the ledger. Tests use disposable SQL and stop the actual invoice service at an injected provider boundary; no live invoice was created.
- The payment panel now exposes administrator/business-owner review for held financial notices. Reviewers can record a provider receipt and allow remaining channels to continue, or close the notice without more sends. Both actions require evidence and append an audit record containing the authenticated reviewer identity; channel barriers are retained. Request IDs make lost-response retries idempotent, and changed evidence, stale attempts, active workers and wrong-job requests are rejected. Disposable SQL checks cover rollback and replay; HTTP tests cover role/identity boundaries and safe errors. A synthetic 320px dark-mode preview fits without horizontal overflow, keeps action targets at least 44px high, and reuses its request ID after a failed submission. This is not authenticated production or owner-device acceptance. The new review table must be included in the unreleased migration; no production review or message was submitted.
- The financial-notice worker rechecks current quote, payment/refund totals, closeout state and recipient/consent before each channel reservation. Portal events commit before sending. Direct Gmail and SMS adapters use bounded waits; ambiguous results and legacy history without a confirmed receipt go to review, without automatic provider fallback. Each channel has a durable send token and hashed destination; successful channels survive retries and uncertain attempts cannot resend. Messages link to the current job portal without embedding a stale balance or provider payment link. A nonoverlapping startup sweep requires both ledger and notification flags. Disposable tests cover payment/consent changes between sends, stale/canceled invoices, refunds, portal-only delivery, unavailable channels, lost reservation commits, lost send acknowledgements and legacy history. The harness is registered in PostgreSQL CI. Provider acceptance is not an inbox/delivery receipt; actual Gmail/SMS acceptance and controlled owner/customer acceptance remain open. A change after the final database check can still precede provider acceptance, which is why message copy refers to current portal state. Flags remain off and no live message was sent.
- Invoice retry acceptance now invokes the real lead-invoice service with a simulated idempotent provider. Lost responses at customer, order, invoice and publish phases reuse one resource per phase; local insert failures retry without resetting paid records. Changed amount/description retries fail on a payload conflict. This is isolated orchestration evidence, not Square HTTP/API acceptance; mutable request recovery and signature-to-effects checks remain open.
- Canonical payments: unique provider/payment identity, integer-cent USD amounts, approved source quote, current quote/lead-total agreement, cumulative coverage and gift-funded exclusions. Payments and paid markers commit together under a job row lock.
- Refunds: unique refund identity, original-payment association, cumulative amount/funding limits, and net reconciliation. Refund-first delivery records the verified original payment and refund atomically without briefly marking the job paid. Tipped refunds require explicit allocation and currently fail closed.
- Square adapters: retrieve payment/refund records from Square, validate completed status, location, currency, funding and stored order/job/quote association. Sandbox and production identities are separate. The signed webhook calls these adapters only when both ledger and Square flags are enabled.
- Reward settlement: uses the persisted award amount/rate on retry, validates recipient/job identity, and commits reward record, wallet credit and settlement marker atomically. Ambiguous legacy reward history requires reconciliation. Advisory locks remain on one checked-out connection.
- Canonical reward funding: uses net payment-ledger funding and approved quote totals. Wallet settlement rechecks completion, payment coverage, refunds and reward basis under the job lock. Gift-funded dollars do not earn ordinary customer rewards.
- Durable reward queue: unique handoffs, atomic enqueue after completed/full payment, a sweep for payment-before-completion, expiring claims, stale-worker fencing and bounded retry timing. The worker verifies durable customer/crew settlement before finishing the claim. Pending customer claims remain explicit ledger reservations.
- Admin reconciliation: an authenticated admin/owner endpoint and expandable job panel show payments, refunds, mismatches, paid/reward markers and queue attempts/status. Disabled retries display as paused. The report does not claim to audit every wallet transaction.
- Existing-path guards: wallet intent does not imply payment; underpaid/deposit invoices do not establish full-job settlement; invoice sync uses the same classification and bypasses legacy accounting in canonical mode. Shop-card grant failures propagate for webhook retry.
- Overpaid invoices retain their collected amount for reconciliation, but job accounting and cash-credit grants cap at the job total. Fourteen classification tests passed, including overpayments with and without a prior deposit. Excess collection does not authorize an automatic refund.
- Invoice effect claims distinguish completed duplicates from work in progress. Each attempt has a fresh ownership token, so an expired handler cannot complete or fail its replacement. Busy deliveries remain retryable. Disposable tests cover additive schema repeatability, legacy completed invoices, expiry, same-event retries and stale writes; the harness is also registered in PostgreSQL CI. Webhook events now also use attempt ownership tokens, and reject an existing event ID with a changed payload hash. Disposable event tests cover stale completion/failure, failed retries and legacy completed history. Complete provider-flow acceptance remains open; claim ownership does not make every side effect atomic.

## Flags and deployment prerequisites

All new flags are disabled by default:

| Flag | Effect |
| --- | --- |
| `JOB_PAYMENT_LEDGER_ENABLED` | Enables canonical ledger services and invoice coverage requirements; Square routing also requires its adapter flag. |
| `SQUARE_JOB_PAYMENT_LEDGER_ENABLED` | Routes supported signed Square payment/refund events into canonical adapters. |
| `JOB_PAYMENT_REWARDS_ENABLED` | Allows canonical reward settlement and queue operations. |
| `JOB_INVOICE_RECONCILIATION_ENABLED` | Enables invoice collection recovery, including provider cancellation, when both ledger and Square adapter flags are enabled. Default off; migration and provider/owner acceptance are required before activation. |
| `JOB_INVOICE_REPLACEMENT_ENABLED` | With ledger, Square adapter and reconciliation enabled, resumes saved replacement requests and attaches their invoices. Requires replacement/intent/phase tables and controlled provider acceptance. Default off. |
| `JOB_PAYMENT_REWARD_WORKER_ENABLED` | Along with the ledger/reward flags, starts the bounded worker sweep. |
| `JOB_FINANCIAL_NOTIFICATIONS_ENABLED` | Along with the ledger flag, starts canonical portal/email/SMS delivery. Requires all three financial notice tables and the regional event/delivery schema. Keep disabled until operator review and controlled delivery acceptance pass. |

Apply and verify the additive schema before enabling these flags. Existing ledger rows need approved-quote backfill before a non-null quote-revision column can be introduced. No production flag, payment migration, wallet issuance or live restore has been performed in this work.

It rechecks the approved quote, exact verified payment coverage without refunds/overpayment, completed job, closeout approval, unchanged invoice bindings and current generation/lease. Only noncollectible provider outcomes permit a fully funded closeout to become paid; lead/closeout balances and queue completion commit together. Disposable tests inject a lead-write failure after the closeout update, retry without recanceling, and introduce payments/new invoices before finalization. The collection worker and periodic backlog scan are implemented behind disabled flags. `check-invoice-reconciliation-worker.ts` runs the actual worker against a disposable database, including own-order versus other-order payments, partial balances, changes during provider inspection, refund/unverified-paid retry cases and missing-request recovery. Its default-provider case uses the installed Square SDK with intercepted invoice/order/cancel HTTP and rejects a different seller location. Provider requests are bounded. Invoice reconciliation handoff is durable: new payment/refund rows enqueue the affected job in their own transaction, and final-invoice publication acknowledgement commits its request with publication metadata. `job_invoice_reconciliation_queue` is additive to `JOB_PAYMENT_LEDGER_SCHEMA` and must exist before enabling the ledger. Requests accumulate even while claiming is disabled. One row per job has a generation; new work preserves an active lease but prevents its older generation from completing the new request. Expired claims use replacement tokens and failures retry after a delay. Existing canonical-invoice and publication SQL harnesses cover transaction rollback, duplicate suppression, changes during claims, lease replacement and retry delay. These are controlled interleavings, not proof of a running provider worker. Production backlog/provider acceptance, pre-provider invoice intent and final customer messaging/review handling remain open. No production migration or worker was started.

Tests invoke the actual service with simulated responses and execute the acknowledgement SQL against disposable databases. The cancellation helper does not refund payments, delete drafts or run automatically when another payment arrives.
